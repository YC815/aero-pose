## 沒做：需要現場資料

### 1. 確認波動主因（先做這個）

A–C 已修，但哪個是主因沒量過；D（趴低時髖部被上半身擋住，torsoPitch 跟著跳）只是推論。

1. 實機上請一個人站上膠帶、趴低不動：`sudo backend/.venv/bin/aero record --source orbbec --name still --seconds 10`
2. `backend/.venv/bin/aero jitter --replay still`
3. 對照結果處理：

| 看到 | 代表 | 處置 |
| --- | --- | --- |
| 寬限期幀多（> 5%） | MediaPipe 常掉偵測 | 先看光線、背景；再試 `pose_landmarker_heavy`（要重量 detect 時間） |
| 某關節 `vis<0.5` 高、`穿越0.5` 多 | visibility 在門檻附近晃 | 遲滯已處理；還是多就把 `VIS_OFF`（`tracker.ts`）往下調 |
| 某關節 `深度用估值` 高 | 深度取不到或在背景上 | 看 `data/doctor.png` 的彩色與深度有沒有對齊；試 `AERO_ORBBEC_ALIGN=hw` |
| 軀幹俯仰標準差大，但髖部 vis 正常、深度用量測值 | 推論 D：髖部像素取到肚子的深度 | 髖部深度改用「肩深度 + MediaPipe world 的肩髖 z 差」；或相機架高往下俯拍 |
| 每個關節標準差都大（> 2 cm） | 純雜訊 | 設定面板把 `filter_min_cutoff` 從 1.0 降到 0.5、0.3，邊降邊看騎士跟手延遲能不能接受 |

### 2. 效能

後端 perf log（README）已經 30 Hz。前端沒量過，拿掉的模糊是推論出來的最大成本，不是量測結果。

要再優化，先收兩樣東西：

- 錄製中的一行後端 perf log。
- Chrome DevTools → Performance，錄製狀態下錄 10 秒（看 Rendering / Painting 佔比、掉幀）。

還沒動、等數據再決定的候選：

- `num_poses` 3 → 2（`pose.py`）：每多一個人就多跑一次關節模型，攤位後面人多時 detect 會變慢。風險是玩家被擠出前 2 名。
- `render_frame`（JPEG 編碼約 5 ms）移出 pipeline thread：現在和 detect 串行，step 約 27 ms，離 33 ms 預算不遠。
- 每個人的 mask 都複製一份 float32 全解析度（`pose.py` 的 `_mask_2d`），可以改成 bool 或只留選中者。

### 3. 輪播

- 第 3 張側面小人趴下的角度看得懂。
